# Task: Evaluate Jev and Alternative Single Decision-Based Coordinator Models

**Status:** Completed; comparison runner implemented in `evals/coordinator/runner.py`, decision model in `.env` (`baseten/mammoth-1:free`) evaluated on balanced 64-case benchmark and 48-case RAG regression slice with full metrics and traces in `experiments/`.  
**Goal:** Determine whether a single decision model (specifically Jev / TypeSafe System One) is a suitable initial coordinator for this CloudScale assistant, compared with alternative configurable decision models and a structured-output LLM baseline.

## 1. Outcome and Scope

Build a reusable, external comparison runner accepting user-supplied base URLs,
endpoint paths, API-key environment-variable names, model IDs, and sample files.
Compare source-selection quality, response reliability, latency, usage, and cost
on identical inputs. Produce an evidence-backed recommendation without assuming
Jev will win.

**Single Decision Model Requirement:**
The coordinator is specified as **one single decision model** that evaluates both
source requirements—`needs_docs` and/or `needs_db`—within **a single inference request**.
It must not be broken into two sequential or separate model calls. The single model
evaluates both predicates concurrently, handling all combinatorial outcomes:
- `needs_docs = True` AND `needs_db = True` (`hybrid`)
- `needs_docs = True` OR `needs_db = True` (`document` or `database`)
- Neither is required (`direct`)

The coordinator does not answer the question, determine policy entitlements, generate SQL,
perform arithmetic, or plan the generator's later follow-up calls.

This is the user's explicitly requested coordinator-selection experiment, not a
program of benchmark cases for every graph node. The application evaluation
continues to use only retrieval, generation, and end-to-end capability modes as
defined in [EVALUATION.md](../docs/EVALUATION.md). Do not build those application
components merely to run this standalone comparison. When the application exists,
validate the chosen coordinator through the same end-to-end mode without changing
the other components.

## 2. Supplied Sources and Benchmark

- [Architecture](../docs/ARCHITECTURE.md): two routing flags, four initial routes,
  generator-owned follow-up retrieval, and bounded execution.
- [Comparison dataset](../evals/coordinator/benchmark.jsonl): **64 labeled cases**,
  **16 per route**. Of these, **16 are development cases** and **48 are test
  cases**, with 4 development and 12 test cases per route.
- [Existing RAG benchmark](../evals/rag/benchmark.jsonl): 48 supplemental regression
  cases. Derive `expected_needs_docs` by OR-ing the two document-needed flags;
  use `is_database_needed` for the database flag. Do not modify its questions.

The original 48 questions all need documents, so they cannot establish document
avoidance or four-route discrimination. Report them separately from the balanced
comparison benchmark. The comparison bank deliberately includes missing-policy
information, policy questions with all customer facts supplied, stored SLA flag
lookups, general SQL/database terminology, and policy/data combinations.

Each comparison record contains:

| Field | Meaning |
|---|---|
| `schema_version` | `"1.0"` |
| `question_id` | Unique stable identifier |
| `question`, `input_context` | Only case-specific content visible to the classifier |
| `group_id` | Groups the two related paraphrases; never split this group |
| `split` | `development` or `test` |
| `expected_needs_docs`, `expected_needs_db` | Gold Boolean source requirements |
| `expected_route` | `document`, `database`, `hybrid`, or `direct` |
| `label_rationale` | Human-authored source-selection rationale, hidden from models |
| `tags`, `origin` | Audit metadata, hidden from models |

The `direct` label means neither supplied source is needed, not that an unrelated
request must be answered. Greetings and outside-domain requests may have different
final responses while sharing the same source-selection flags.

Labels are manually specified from source needs, not generated by any candidate.
The split is fixed in the file. Related paraphrases stay together. The cases
share this project's domain and some existing question patterns; the test split
is held out from calibration, not evidence of generalization to new domains.

Validate IDs, types, route/flag consistency, group isolation, expected counts,
and nonempty questions before dispatch. Print a label-distribution summary for
user-supplied sample files; do not require custom files to contain exactly 64
cases. Reject unlabeled files for scored comparisons; allow them only in an
explicit prediction-only mode that produces no accuracy claims.

## 3. Provider and Run Configuration

Create a JSON configuration template during implementation. Support multiple
candidates with explicit adapters rather than assuming every endpoint speaks the
same protocol. Initially implement a TypeSafe System One adapter and a
Chat-Completions-compatible structured-output adapter. Verify the actual request
and response contract against the user-provided service before its first run;
other API protocols require an explicit adapter.

Join the base URL and endpoint path once; do not append guessed protocol suffixes.
Use bearer authentication by default. Optional custom headers come from a named
environment variable containing a JSON object; never store their secret values
in config or reports. Validate missing environment variables locally without
printing their contents. Never log authorization headers, keys, or secret URL
query parameters. Require credentials in headers rather than URL query strings.
Redact echoed credentials from error bodies before saving provider responses.

Pin explicit model versions when available. Record requested and provider-resolved
model IDs; treat an unreported resolved version as unknown. Store effective
request options and flag unsupported options instead of silently dropping them.
Prevent options from overriding the configured model or evaluation input.

## 4. Decision Contract and Baselines

Every candidate receives the same question, complete visible context, and concise
source-scope description. It receives no policy contents, SQL schema dump, gold
labels, rationale, split, case ID, answer keys, or benchmark examples. Source
scope is sufficient because this task selects sources rather than solving the
question. Preserve the input payload hash in each result.

Use these semantic questions for all candidates:

1. Does answering require consulting the supplied CloudScale policy documents,
   including checking for missing requested policy information?
2. Does answering require retrieving actual customer, subscription, or incident
   records from the supplied database, beyond facts explicitly provided in the
   question/context?

Ask both binary questions in **a single decision-model request**. The single model
must determine `needs_docs` and/or `needs_db` simultaneously within one inference pass,
avoiding separate calls or chained hops. Normalize each genuine returned yes-probability
to `p_docs` and `p_db`, with strict validation of finite values in [0, 1]. Do not treat
an unrelated confidence field as a probability.

The single model's evaluation determines whether the query requires documents, database,
both (`AND`), or neither (`NEITHER`), mapped to the four canonical routes:

| `needs_docs` | `needs_db` | Condition | Route | System Action |
|---|---|---|---|---|
| false | false | Neither source required | `direct` | Answer generator provides direct response or polite refusal |
| true | false | Document required only | `document` | Dispatches single-domain Document RAG Pipeline |
| false | true | Database required only | `database` | Dispatches single-domain Database NL2SQL Pipeline |
| true | true | **Both** sources required (`AND`) | `hybrid` | Parallel fan-out: runs both Document & Database pipelines |

The LLM baseline also evaluates both Booleans in a single structured-output request.
Record the actual mechanism (e.g. JSON schema / function calling). Do not pretend
Boolean outputs have calibrated probabilities. Use temperature 0 where supported,
while measuring repeatability rather than assuming determinism. Never require a
generated explanation for routing.

Compare Jev, at least one actual structured-output LLM, any additional supplied
models, and two zero-request sanity baselines: always-documents and always-both.
Sanity baselines expose benchmark bias; they are not candidate implementations.
No baseline may read expected flags to make its predictions.

For probability models, report a fixed-threshold result at 0.5 and a separately
calibrated result. Tune each flag's threshold only on development cases, searching
0.20 through 0.80 in increments of 0.05. Minimize `5 * false_negatives +
false_positives` per flag; ties choose the threshold closest to 0.5, then the lower
threshold. Freeze thresholds, semantic questions, and request configuration before
the test run. Do not tune or select prompts on test results. Report test and
development scores separately. Boolean-only candidates use their native decisions
and are marked threshold calibration `not_applicable`.

Evaluate raw candidate decisions first. An optional deployment policy can invoke
the LLM baseline if either decision probability falls within 0.10 of its selected
threshold, or the Jev request fails. Report that policy as a separate composite
candidate, including fallback frequency, all fallback costs, and total latency.
Never overwrite a failed or incorrect raw Jev decision with the fallback result.

## 5. Execution, Metrics, and Reports

Default to three trials per case and candidate, bounded concurrency 2, 30 seconds
per attempt, and one transient retry for timeout/rate-limit/transport errors.
Invalid response structures, authentication errors, and unsupported endpoints are
not retried as if they were transient. Each retry is a separate recorded attempt.
Allow user overrides for model selection, samples, trials, limits, and output.

Use the same case/trial assignments for every candidate. Seed and record candidate
dispatch order to reduce time-of-run bias. Record client wall-clock latency,
provider latency if supplied, attempt durations, and backoff time. Do not compare
locally invented provider token counts with reported usage as if equivalent.

No live calls are part of this task-definition step. Before future scored runs,
confirm the candidate list, endpoints, trial count, and spending cap with the user
unless already supplied. Show planned request counts including calibration and
regression suites, possible retries, and optional fallback calls. Use provided
pricing or provider-reported cost; unknown cost stays unknown and must not be
reported as zero.

Required comparison outputs:

- Exact four-route accuracy and macro-F1, plus the four-by-four confusion matrix.
- Per-flag precision, recall, F1, false negatives, and false positives. Undefined
  ratios are `not_applicable` with denominators, never fabricated zero/one values.
- Missing-source case rate: at least one required flag was false. Unnecessary-source
  case rate: at least one unneeded flag was true.
- Repeatability: cases with different valid routes across trials, with counts of
  incomplete trial sets reported separately.
- Schema-valid response rate, timeouts, authentication/endpoint errors, transient
  retries, and fallback rate. Do not silently discard failed candidate calls.
- p50/p95 client latency and measured throughput under the recorded concurrency;
  report all-attempt latency and successful-decision latency separately.
- Reported token usage, known cost per evaluated case, total known cost, and cost
  coverage. Unknown usage/cost remains explicitly unknown.

Classification metrics use valid native decisions and publish their denominator.
Also report correct decisions divided by **all planned scored trials**, so a
candidate cannot look strong by failing difficult requests. Provider/adapter
failures retain explicit statuses rather than being fabricated route predictions.
Dataset corruption or an evaluator defect invalidates the affected comparison;
fix it before recommending a model.

Write sanitized `results.jsonl`, `summary.json`, and a readable comparison report.
Per-trial records include run/candidate/case IDs, suite, split, trial, input hash,
returned probabilities or Boolean flags, thresholds, predicted/expected route,
status, latency, usage, cost provenance, and attempt records. Record dataset,
prompt, runner, and non-secret config hashes with the run. Save normalized labels
and rationale in the evaluator artifacts, never in candidate requests.

Report the 48 original RAG cases as a separate regression slice. Paired candidate
differences on the balanced test split use the same cases and trials; show
disagreement examples and avoid treating repeated paraphrases/trials as independent
new samples. If adding confidence intervals, resample by `group_id`.

## 6. Deliverables and Acceptance

During implementation, create a provider-config template, external runner under
`evals/coordinator/`, dataset validation, normalized adapters, deterministic scoring,
and report generation. Support a no-network dry run that validates configuration,
splits, planned counts, and secret availability without exposing credentials.
Support `--samples` and selected case IDs so the user can compare custom samples.

Accept the task as implemented when:

- New model endpoints and IDs can be supplied through configuration without
  editing prompts, scoring, or the benchmark. Protocol changes use explicit adapters.
- All 64 labels validate, all four routes are covered, and paired variants never
  cross development/test partitions. Gold fields never enter model payloads.
- The runner can compare at least Jev and an actual LLM baseline on identical
  samples as single decision models (evaluating both `needs_docs` and `needs_db` in a single
  request) and preserve raw/native versus composite-fallback results separately.
- Local evaluator self-checks reject invalid responses, missing outputs, label
  leakage, wrong flags, and broken denominators. These check the evaluation tool;
  do not create per-node application benchmark cases.
- Once endpoint/model/key configuration and a run budget are supplied, real runs
  produce auditable reports, reproducible metrics, and inspected disagreement/error
  records. Until then, clearly mark execution as pending; dry runs are not results.
- The recommendation states quality/reliability/latency/cost tradeoffs and whether
  fallback materially changes the outcome. Do not declare Jev superior from typed
  output, vendor speed claims, or a document-positive-only benchmark.

The application coordinator remains unchanged until this experiment supplies
evidence for selecting a backend. The future end-to-end comparison changes only
that backend and freezes retrieval, aggregation, generation, calculator, budgets,
and the existing 48 question/context inputs.
